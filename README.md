# CS230-OperatingPlatforms
For this course, I submitted my completed software design document for The Gaming Room into my GitHub portfolio. This document represents the full design process for the Draw It or Lose It game engine and shows how I approached translating user requirements into a structured, scalable software architecture.

The Gaming Room was the client, and they wanted a Java‑based game engine that could support multiple games, teams, and players while preventing duplicates and maintaining consistent data. They also needed the design to be flexible enough to later expand into a web‑based, distributed environment. Their main requirements included unique game names, centralized management of game entities, and a design that uses object‑oriented principles and patterns like the singleton and iterator.

One thing I did particularly well in developing this documentation was clearly explaining how the design constraints influenced the architecture. In the Design Constraints section, I described how the need for future web deployment shaped decisions like using a singleton GameService and keeping entity relationships clean and modular. I also feel that the Evaluation and Recommendations sections were strong because they directly tied platform analysis to the client’s needs, especially the justification for choosing Linux as the recommended operating platform.

Working through the design document before writing the code was extremely helpful. It forced me to think about the relationships between Game, Team, and Player, and how the GameService would manage them. By outlining the UML model and identifying where inheritance and encapsulation were needed, the actual coding process became much more straightforward. The design document acted like a blueprint that kept me organized and prevented me from writing code that didn’t fit the overall architecture.

If I were to revise one part of the document, I would improve the System Architecture View section. Even though the project didn’t require a full architecture diagram, I could expand this section with a more detailed explanation of how the game engine would interact with future web components, such as REST APIs or load balancers. Adding a simple logical topology diagram would make the document even more complete.

To interpret the user’s needs, I focused on the core problems The Gaming Room described: preventing duplicate names, supporting multiple teams and players, and preparing for distributed deployment. I implemented these needs by using the singleton pattern to centralize game management and the iterator pattern to search for duplicates. Considering user needs is essential because the software must solve the client’s actual problems, not just meet technical requirements. If the design doesn’t reflect the user’s workflow or constraints, the final product won’t be useful.

My approach to designing the software was to break the problem into layers: entity modeling, service management, constraints, and future scalability. I relied heavily on object‑oriented design principles, UML modeling, and pattern‑based architecture. In the future, I would continue using techniques like UML diagrams, design patterns, and platform evaluations to analyze and design similar applications. These strategies help ensure that the final codebase is organized, maintainable, and aligned with the client’s long‑term goals.
